# Контракты в коде и их отличия от схем

Код: `src/contracts`. Норма: `docs/spec/harness-spec`. Этот файл перечисляет места, где код уточнил схемы.

Состояние на 2026-11-11: отличия M1 - M7, J1, J3, P1 - P4 внесены в схемы (`harness-manifest` 1, 3, 5, 7; `harness-journal` 1, 2; `harness-connector` 1; `harness-core` 3; `harness-instance-mr-review` 2).
Оба примера манифеста в схемах проходят валидатор. Открыты M8 и J2.

## Манифест

| № | Отличие | Причина |
|---|---|---|
| M1 | Файл манифеста это JSON. Пример в схеме записан как YAML | Ядро не имеет зависимостей npm, разборщика YAML нет |
| M2 | Поле `collect.flags`: список признаков, которые возвращает скрипт сбора. `run_if` должен быть в этом списке | Опечатка в имени признака иначе не видна до запуска |
| M3 | Формат результата `findings` из примера схемы не принят. Список закрыт: `list, table, text, file` | Страница 1 схемы задаёт четыре вида. Пример на странице 5 им противоречит |
| M4 | Запись в конверте требует поле `env` | Правило «конверт не действует на производственную среду» нельзя проверить без имени среды |
| M5 | Без пакета проверяется только структура. Для подключения пакет обязателен | Черновик манифеста проверяется в редакторе без пакета |
| M6 | Пакет без списка сред не допускает записи в конверте | Неизвестная среда считается производственной |
| M7 | Предел возвратов: от 0 до 5 | Схема не задаёт верхнюю границу |
| M8 | Форма входа триггера не описана в коде | Схема называет её, но не задаёт формат |

## Журнал

| № | Отличие | Причина |
|---|---|---|
| J1 | Источников семь: `task, policy, check, executor, memory, craft, harness`. Схема называет пять на странице 1 и шесть групп на странице 2 | Источник это префикс вида события |
| J2 | Обязательные поля данных заданы для семи видов событий из 44 | Остальные виды получат поля вместе с кодом, который их пишет |
| J3 | Строковое значение в данных это метка до 80 знаков без пробелов. Имя поля данных это идентификатор | Так свободный текст не попадает ни в значение, ни в имя поля |

## Политика

| № | Отличие | Причина |
|---|---|---|
| P1 | Вид действия `local`: изменение внутри рабочего дерева, по умолчанию разрешено | Без него каждая правка файла требует вопроса. Изменение покрыто отпечатком состояния |
| P2 | Решение по умолчанию это решение слоя ядра. Нижний слой не может его ослабить | Следует из правила «нижний слой только ужесточает» |
| P3 | Для конверта записью считается любое действие, кроме известного чтения и локального изменения | Команда оболочки без класса, о которой спросило правило слоя, не проходит через конверт в производственной среде |
| P4 | Исход слоя вне списка считается отказом | Решения слоёв приходят из данных пакета |

## Gate

Код: `src/gate`. Это модули `agentic` v0.5.8 без изменения логики, формат CommonJS. Решения держит корпус `test/data/gate-decisions.json`: 408 случаев.

| № | Отличие от схем | Причина |
|---|---|---|
| G1 | Каждое решение gate идёт как решение слоя ядра, включая правила из личного файла и файла репозитория | Gate не сообщает, из какого слоя пришло правило |
| G2 | Имя действия для политики это идентификатор правила gate, цель пустая | Описания действий коннектора ещё нет |
| G3 | Классы `data, publish, git-discard, blast-radius, protected` помечены как неизвестная среда: конверт на них не действует | Идентификатор правила не называет цель. В `agentic` эти классы утверждались по одному действию |
| G4 | `allow_forms` не перенесён | Решение R3: его заменяет конверт |
| G5 | `gate-mcp.cjs` разбирает имена вида `mcp__сервер__инструмент` и знает сервер `ccd_pr` | Это часть адаптера клиента. Модуль перенесён целиком, потому что `gate.cjs` берёт из него правила для `gh` и `glab` |

Не перенесено: `perimeter`, `protect`, `sandbox`, фильтр `hook.sh`, корпус `gitref` (50 случаев: он идёт через хук).

## Пакеты

Код: `src/packs/packs.ts`. Пример: `examples/packs`.

| № | Отличие от схем | Причина |
|---|---|---|
| K1 | Состав каталога: `pack.json`, `manifests/*.json`, `collect/`, `check/` | Схема называет файлы, но не задаёт раскладку |
| K2 | Коннекторы и список известных сред задаёт только организация. Нижний уровень может сузить список коннекторов и добавить производственную среду | Следует из правила «нижний уровень сужает». Нижний уровень иначе мог бы объявить неизвестную среду известной |
| K3 | Список, которого не дал ни один пакет, при проверке манифеста означает «ничего» | Без этого манифест проходил проверку, когда ни один пакет не содержал скриптов |
| K4 | Пакет с ошибкой не подключается целиком. Его манифесты не читаются | Схема: «пакет не подключается» |
| K5 | Одинаковый скрипт или одинаковая проверка в двух пакетах это ошибка нижнего пакета | Имена не повторяются, как у сценариев |
| K6 | Символическая ссылка не считается файлом пакета | Скрипт не может указывать за пределы пакета |
| K7 | Предел это наименьшее значение по уровням. Большее значение нижнего уровня ничего не меняет и ошибкой не считается | Схема: «берётся наименьший» |
| K8 | Роли исполнителей задаёт организация, нижний уровень может только сузить список | Роль это разрешение: манифест запускает только разрешённых исполнителей |
| K9 | Если пакет уровня не подключён, пакеты уровней ниже тоже не подключаются | Пределы неподключённого уровня теряются. Без этого правила пределы открываются |
| K10 | Манифест называет скрипт сбора только из `collect/`. Два файла с одним именем и разными расширениями это ошибка пакета | Иначе неясно, какой файл запустится |
| K11 | Имя проверки в `pack.json` не связано с файлом в `check/` | Формат проверки вида «команда» ещё не задан |

Не покрыто в коде пакетов: барьеры из пакетов (слои правил gate читаются отдельно, `src/gate/config.cjs`), уровни модели по умолчанию, сроки вето, язык и тон, версия пакета и откат, запись итога слияния в журнал.

## Исполнение задачи

Код: `src/core/task.ts` (автомат состояний), `src/core/runtime.ts` (хранение и журнал), `src/core/collect.ts` и `collect-child.ts` (скрипт сбора), `src/journal/writer.ts`.

| № | Отличие от схем | Причина |
|---|---|---|
| T1 | Состояний шесть: подготовка, исполнение, проверка, ожидание человека, закрыта, пропущена. «Отчёт подан» это переход, а не состояние | Между отчётом и проверкой ничего не происходит |
| T2 | У ожидания человека три причины: вопрос гейта, предел возвратов, утверждение результата. Ответ на вопрос гейта не утверждает результат | Одно состояние в схеме покрывает три разных ожидания |
| T3 | У события есть источник: агент, человек, харнес. Агент может только подать отчёт и задать вопрос | Иначе правило «агент не закрывает задачу» держится только на вызывающем коде |
| T4 | Свободная задача закрывается отчётом агента с меткой «не проверено» | Схема, правило 4 контура: шаг проверки пропускается |
| T5 | Сбой сбора закрывает задачу с меткой «не проверено» и строкой `harness.failure` | Схема не описывает сбой сбора |
| T6 | Скрипт сбора получает входы как JSON на стандартный ввод и печатает один объект `outputs` и `flags` с именами из манифеста. Лишнее поле это ошибка | Схема не задаёт формат обмена |
| T7 | Скрипт запускает отдельный процесс-надзиратель в своей группе процессов. По пределу времени или размера убивается вся группа | Иначе дочерний процесс скрипта переживает предел |
| T8 | Запись в файл задачи идёт под файлом блокировки. Занятая блокировка даёт ответ «занято», решение по действию тогда принимается без конверта | Хуки это отдельные процессы. Без блокировки два процесса засчитывают одно и то же последнее использование |
| T9 | Поле манифеста `version`: версия сценария, по умолчанию 1 | Строка журнала требует версию сценария, в манифесте её не было |
| T10 | Подтверждение записи конверта принимает только открытая задача | Иначе в журнал идёт строка по закрытой задаче |

Не покрыто: приостановка задачи при новом триггере, продолжение задачи в другой сессии, срок бездействия (событие `expire` есть, таймера нет), задача с договором, запуск проверок кроме сверки цитат, ограничение скрипта сбора коннекторами чтения, верхний предел для `timeout_s` и `max_bytes` из манифеста.

## Сверка цитат

Код: `src/check/citations.ts` (сверка), `src/core/runtime.ts` (`submitReport`, `runCheck`). Окно ±3 строки, цитата от 8 знаков, предел файла 1 МБ и проверка пути перенесены из `agentic` v0.5.8 `lib/review.js` без изменения логики. Разбор текстовой строки находки из `agentic` в ядро не вошёл.

| № | Отличие от схем и от `agentic` | Причина |
|---|---|---|
| C1 | Сверка даёт ответ проверки: `PASS`, `FAIL` или нет ответа. В `agentic` это была метрика | R12: сверка цитат это вид проверки, ответ влияет на метку |
| C2 | Находка, которую нельзя сверить, это `FAIL`: нет файла и строки, нет цитаты, цитата короче 8 знаков, файла нет в источнике, файл не входит в список `done.changed`, цитаты нет в окне. В `agentic` это было «не проверено» | Правило схемы: каждая находка подтверждена источником |
| C3 | Отчёт это данные: один объект JSON `{"items": [...]}`. Ограда кода вокруг объекта допустима, другой текст нет. Пустой список это верный отчёт | Формат текста с английскими словами был форматом одного рецензента. Ядро не должно его знать |
| C4 | Ядро читает у находки поля `file`, `line`, `end`, `quote`, `text`. Остальные поля и их значения называет манифест: `output.fields`. Поле вне манифеста, пропуск названного поля или значение вне списка это `FAIL`. Названное поле всегда имеет закрытый список значений: свободный текст находки идёт только в `text` | Что такое находка и какими словами её оценивают, решает пакет |
| C5 | Находок больше предела (`output.max_items`, не больше 10) это `FAIL`. В `agentic` лишние находки не читались | Схема: находок не больше десяти |
| C6 | Нет ответа только при сбое харнеса: нет источника, истёк срок, отчёт не читается | Правило 3 проверки: молчание не успех, но и не вина отчёта |
| C7 | Поля манифеста `done.source` и `done.changed`: имена результатов сбора с каталогом источника и списком изменённых файлов. Манифест со сверкой цитат без `done.source` не подключается. `done.changed` по выбору: с ним находка вне изменённых файлов это `FAIL` | Источник задаёт харнес, а не агент. Схема не говорит, откуда сверка берёт источник |
| C8 | Послабление `agentic` для изменённого файла снято: цитата из изменённого файла сверяется как любая другая | Источник это снимок от шага сбора, он не меняется за время задачи |
| C9 | Агент подаёт отчёт текстом через `submitReport`. Ядро хранит текст рядом с задачей и сразу запускает сверку. Прямое событие отчёта или ответа проверки для такой задачи запрещено | Правило 1 проверки: проверку запускает ядро |
| C10 | Ответ считается и применяется под одной блокировкой. Срок сверки не больше половины срока блокировки. Если ответ не был применён, задача остаётся в проверке и `runCheck` запускает сверку снова по сохранённому отчёту | Иначе сбой между отчётом и ответом оставляет задачу без выхода |

Открыто:
- Ответ «нет ответа» при сбое харнеса возвращает задачу агенту и тратит один возврат. Так автомат работал и до сверки. Варианты: не считать возврат или сразу ждать человека.
- Источник это каталог с файлами, место это файл и строка. Цитату из тикета, страницы или лога сверка не проверит. Нужен источник как набор именованных текстов.

Не покрыто: виды проверки «команда», «артефакт» и «внешнее состояние», привязка ответа к состоянию работы (правило 2), показ оператору отметки «цитата сверена» по каждой находке, вид отчёта для человека (его строит клиент из данных).

## Чего в коде нет

- Сопоставление вызова инструмента с правилами. Для команды оболочки это делает `src/gate`.
- Очередь отложенных действий.
