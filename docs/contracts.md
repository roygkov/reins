# Контракты в коде и их отличия от схем

Код: `src/contracts`. Норма: `docs/spec/harness-spec`. Этот файл перечисляет места, где код уточнил схемы.

Состояние на 2026-11-11: отличия M1 - M7, J1, J3, P1 - P4 внесены в схемы (`harness-manifest` 1, 3, 5, 7; `harness-journal` 1, 2; `harness-connector` 1; `harness-core` 3; `harness-instance-mr-review` 2).
Оба примера манифеста в схемах проходят валидатор. Открыты M8 и J2.

## Манифест

| № | Отличие | Причина |
|---|---|---|
| M1 | Файл манифеста это JSON. Пример в схеме записан как YAML | Ядро не имеет зависимостей npm, разборщика YAML нет |
| M2 | Поле `collect.flags`: список признаков, которые возвращает скрипт сбора. `run_if` должен быть в этом списке | Опечатка в имени признака иначе не видна до запуска |
| M3 | Формат результата `findings` из примера схемы не принят. Список закрыт: `list, table, text, file` | Страница 1 схемы задаёт четыре вида. Пример на странице 5 им противоречит |
| M4 | Запись в конверте требует поле `env` | Правило «конверт не действует на производственную среду» нельзя проверить без имени среды |
| M5 | Без пакета проверяется только структура. Для подключения пакет обязателен | Черновик манифеста проверяется в редакторе без пакета |
| M6 | Пакет без списка сред не допускает записи в конверте | Неизвестная среда считается производственной |
| M7 | Предел возвратов: от 0 до 5 | Схема не задаёт верхнюю границу |
| M8 | Форма входа триггера не описана в коде | Схема называет её, но не задаёт формат |

## Журнал

| № | Отличие | Причина |
|---|---|---|
| J1 | Источников семь: `task, policy, check, executor, memory, craft, harness`. Схема называет пять на странице 1 и шесть групп на странице 2 | Источник это префикс вида события |
| J2 | Обязательные поля данных заданы для семи видов событий из 44 | Остальные виды получат поля вместе с кодом, который их пишет |
| J3 | Строковое значение в данных это метка до 80 знаков без пробелов. Имя поля данных это идентификатор | Так свободный текст не попадает ни в значение, ни в имя поля |

## Политика

| № | Отличие | Причина |
|---|---|---|
| P1 | Вид действия `local`: изменение внутри рабочего дерева, по умолчанию разрешено | Без него каждая правка файла требует вопроса. Изменение покрыто отпечатком состояния |
| P2 | Решение по умолчанию это решение слоя ядра. Нижний слой не может его ослабить | Следует из правила «нижний слой только ужесточает» |
| P3 | Для конверта записью считается любое действие, кроме известного чтения и локального изменения | Команда оболочки без класса, о которой спросило правило слоя, не проходит через конверт в производственной среде |
| P4 | Исход слоя вне списка считается отказом | Решения слоёв приходят из данных пакета |

## Gate

Код: `src/gate`. Это модули `agentic` v0.5.8 без изменения логики, формат CommonJS. Решения держит корпус `test/data/gate-decisions.json`: 408 случаев.

| № | Отличие от схем | Причина |
|---|---|---|
| G1 | Каждое решение gate идёт как решение слоя ядра, включая правила из личного файла и файла репозитория | Gate не сообщает, из какого слоя пришло правило |
| G2 | Имя действия для политики это идентификатор правила gate, цель пустая | Описания действий коннектора ещё нет |
| G3 | Классы `data, publish, git-discard, blast-radius, protected` помечены как неизвестная среда: конверт на них не действует | Идентификатор правила не называет цель. В `agentic` эти классы утверждались по одному действию |
| G4 | `allow_forms` не перенесён | Решение R3: его заменяет конверт |
| G5 | `gate-mcp.cjs` разбирает имена вида `mcp__сервер__инструмент` и знает сервер `ccd_pr` | Это часть адаптера клиента. Модуль перенесён целиком, потому что `gate.cjs` берёт из него правила для `gh` и `glab` |

Не перенесено: `perimeter`, `protect`, `sandbox`, фильтр `hook.sh`, корпус `gitref` (50 случаев: он идёт через хук).

## Пакеты

Код: `src/packs/packs.ts`. Пример: `examples/packs`.

| № | Отличие от схем | Причина |
|---|---|---|
| K1 | Состав каталога: `pack.json`, `manifests/*.json`, `collect/`, `check/` | Схема называет файлы, но не задаёт раскладку |
| K2 | Коннекторы и список известных сред задаёт только организация. Нижний уровень может сузить список коннекторов и добавить производственную среду | Следует из правила «нижний уровень сужает». Нижний уровень иначе мог бы объявить неизвестную среду известной |
| K3 | Список, которого не дал ни один пакет, при проверке манифеста означает «ничего» | Без этого манифест проходил проверку, когда ни один пакет не содержал скриптов |
| K4 | Пакет с ошибкой не подключается целиком. Его манифесты не читаются | Схема: «пакет не подключается» |
| K5 | Одинаковый скрипт или одинаковая проверка в двух пакетах это ошибка нижнего пакета | Имена не повторяются, как у сценариев |
| K6 | Символическая ссылка не считается файлом пакета | Скрипт не может указывать за пределы пакета |
| K7 | Предел это наименьшее значение по уровням. Большее значение нижнего уровня ничего не меняет и ошибкой не считается | Схема: «берётся наименьший» |
| K8 | Роли исполнителей задаёт организация, нижний уровень может только сузить список | Роль это разрешение: манифест запускает только разрешённых исполнителей |
| K9 | Если пакет уровня не подключён, пакеты уровней ниже тоже не подключаются | Пределы неподключённого уровня теряются. Без этого правила пределы открываются |
| K10 | Манифест называет скрипт сбора только из `collect/`. Два файла с одним именем и разными расширениями это ошибка пакета | Иначе неясно, какой файл запустится |
| K11 | Имя проверки в `pack.json` не связано с файлом в `check/` | Формат проверки вида «команда» ещё не задан |

Не покрыто в коде пакетов: барьеры из пакетов (слои правил gate читаются отдельно, `src/gate/config.cjs`), уровни модели по умолчанию, сроки вето, язык и тон, версия пакета и откат, запись итога слияния в журнал.

## Исполнение задачи

Код: `src/core/task.ts` (автомат состояний), `src/core/runtime.ts` (хранение и журнал), `src/core/collect.ts` и `collect-child.ts` (скрипт сбора), `src/journal/writer.ts`.

| № | Отличие от схем | Причина |
|---|---|---|
| T1 | Состояний шесть: подготовка, исполнение, проверка, ожидание человека, закрыта, пропущена. «Отчёт подан» это переход, а не состояние | Между отчётом и проверкой ничего не происходит |
| T2 | У ожидания человека три причины: вопрос гейта, предел возвратов, утверждение результата. Ответ на вопрос гейта не утверждает результат | Одно состояние в схеме покрывает три разных ожидания |
| T3 | У события есть источник: агент, человек, харнес. Агент может только подать отчёт и задать вопрос | Иначе правило «агент не закрывает задачу» держится только на вызывающем коде |
| T4 | Свободная задача закрывается отчётом агента с меткой «не проверено» | Схема, правило 4 контура: шаг проверки пропускается |
| T5 | Сбой сбора закрывает задачу с меткой «не проверено» и строкой `harness.failure` | Схема не описывает сбой сбора |
| T6 | Скрипт сбора получает входы как JSON на стандартный ввод и печатает один объект `outputs` и `flags` с именами из манифеста. Лишнее поле это ошибка | Схема не задаёт формат обмена |
| T7 | Скрипт запускает отдельный процесс-надзиратель в своей группе процессов. По пределу времени или размера убивается вся группа | Иначе дочерний процесс скрипта переживает предел |
| T8 | Запись в файл задачи идёт под файлом блокировки. Занятая блокировка даёт ответ «занято», решение по действию тогда принимается без конверта | Хуки это отдельные процессы. Без блокировки два процесса засчитывают одно и то же последнее использование |
| T9 | Поле манифеста `version`: версия сценария, по умолчанию 1 | Строка журнала требует версию сценария, в манифесте её не было |
| T10 | Подтверждение записи конверта принимает только открытая задача | Иначе в журнал идёт строка по закрытой задаче |
| T11 | Седьмое состояние: публикация. Принятый результат (ответ `PASS` или утверждение человека) задачи с записями в конверте не закрывает задачу. Метка итога уже записана, конверт действует | R6: задача включает шаг утверждения и публикации. Схема экземпляра: сверка, одна кнопка, публикация в границах конверта |
| T12 | Публикацию завершает событие `finish` от агента или человека. Человек может остановить публикацию. Событие `expire` закрывает публикацию с уже известной меткой | Агент не меняет итог: метка задана до публикации |
| T14 | Конверт публикации перестаёт отвечать, если задача не менялась час. Срок считается по файлу задачи. Ответ человека на вопрос задачи это изменение задачи: после него срок идёт заново. Задача при этом остаётся открытой: таймера, который закрывает её, ещё нет | Иначе незавершённая публикация оставляет утверждённую запись без срока |
| T15 | Вход в публикацию не пишет своей строки в журнал: в закрытом списке событий такого события нет. Завершение `finish` не пишет причину, остановка человеком пишет `stopped`, срок пишет `expired` | Новое событие это правка контракта журнала |
| T16 | Человек может остановить задачу в любом открытом состоянии. Принятый результат сохраняет метку, остальные задачи закрываются с меткой «не проверено» и причиной `stopped` | Раньше остановка работала только в ожидании человека и в публикации |
| T17 | Конец подготовки пишется под блокировкой и только в задачу, которая всё ещё готовится. Задача, остановленная во время сбора, остаётся остановленной | Сбор идёт долго. Раньше его конец перезаписывал остановку |
| T13 | Конверт действует при исполнении и при публикации. Задача без записей в конверте закрывается сразу, как раньше | Схема манифеста: срок конверта это время, пока задача открыта |

Не покрыто: приостановка задачи при новом триггере, продолжение задачи в другой сессии, задача с договором, ограничение скрипта сбора коннекторами чтения, верхний предел для `timeout_s` и `max_bytes` из манифеста.

## Сверка цитат

Код: `src/check/citations.ts` (сверка), `src/core/runtime.ts` (`submitReport`, `runCheck`). Окно ±3 строки, цитата от 8 знаков, предел файла 1 МБ и проверка пути перенесены из `agentic` v0.5.8 `lib/review.js` без изменения логики. Разбор текстовой строки находки из `agentic` в ядро не вошёл.

| № | Отличие от схем и от `agentic` | Причина |
|---|---|---|
| C1 | Сверка даёт ответ проверки: `PASS`, `FAIL` или нет ответа. В `agentic` это была метрика | R12: сверка цитат это вид проверки, ответ влияет на метку |
| C2 | Находка, которую нельзя сверить, это `FAIL`: нет файла и строки, нет цитаты, цитата короче 8 знаков, файла нет в источнике, файл не входит в список `done.changed`, цитаты нет в окне. В `agentic` это было «не проверено» | Правило схемы: каждая находка подтверждена источником |
| C3 | Отчёт это данные: один объект JSON `{"items": [...]}`. Ограда кода вокруг объекта допустима, другой текст нет. Пустой список это верный отчёт | Формат текста с английскими словами был форматом одного рецензента. Ядро не должно его знать |
| C4 | Ядро читает у находки поля `file`, `line`, `end`, `quote`, `text`. Остальные поля и их значения называет манифест: `output.fields`. Поле вне манифеста, пропуск названного поля или значение вне списка это `FAIL`. Названное поле всегда имеет закрытый список значений: свободный текст находки идёт только в `text` | Что такое находка и какими словами её оценивают, решает пакет |
| C5 | Находок больше предела (`output.max_items`, не больше 10) это `FAIL`. В `agentic` лишние находки не читались | Схема: находок не больше десяти |
| C6 | Нет ответа только при сбое харнеса: нет источника, истёк срок, отчёт не читается | Правило 3 проверки: молчание не успех, но и не вина отчёта |
| C7 | Поля манифеста `done.source` и `done.changed`: имена результатов сбора с каталогом источника и списком изменённых файлов. Манифест со сверкой цитат без `done.source` не подключается. `done.changed` по выбору: с ним находка вне изменённых файлов это `FAIL` | Источник задаёт харнес, а не агент. Схема не говорит, откуда сверка берёт источник |
| C8 | Послабление `agentic` для изменённого файла снято: цитата из изменённого файла сверяется как любая другая | Источник это снимок от шага сбора, он не меняется за время задачи |
| C9 | Агент подаёт отчёт текстом через `submitReport`. Ядро хранит текст рядом с задачей и сразу запускает сверку. Прямое событие отчёта или ответа проверки для такой задачи запрещено | Правило 1 проверки: проверку запускает ядро |
| C10 | Ответ считается без блокировки и применяется под блокировкой к задаче, которая всё ещё ждёт эту проверку. Срок сверки не больше половины срока блокировки. Если ответ не был применён, задача остаётся в проверке и `runCheck` запускает сверку снова по сохранённому отчёту | Иначе сбой между отчётом и ответом оставляет задачу без выхода |

Открыто:
- Ответ «нет ответа» при сбое харнеса возвращает задачу агенту и тратит один возврат. Так автомат работал и до сверки. Варианты: не считать возврат или сразу ждать человека.
- Источник это каталог с файлами, место это файл и строка. Цитату из тикета, страницы или лога сверка не проверит. Нужен источник как набор именованных текстов.

Не покрыто: виды проверки «команда», «артефакт» и «внешнее состояние», привязка ответа к состоянию работы (правило 2), показ оператору отметки «цитата сверена» по каждой находке, вид отчёта для человека (его строит клиент из данных).

## Клиент: путь сценария

Код: `src/cli.ts` (команда `reins`), `src/client/input.ts` (вход задачи для модели), `clients/claude-code` (команда `/reins:run` для Claude Code). Это первая часть адаптера клиента: клиент без хуков запускает сценарий. События клиента «перед действием» и «после действия» ядро ещё не получает.

| № | Отличие от схем | Причина |
|---|---|---|
| A1 | Клиент говорит с ядром через команду `reins`: `scenarios`, `open`, `input`, `report`. Ответ это один объект JSON. Код возврата: 0 готово, 2 задача не закрыта как проверенная, 1 ошибка | Схема клиента задаёт события и решения, но не способ вызова. Команда работает в любом клиенте с оболочкой |
| A2 | Вход задачи это данные: результаты сбора, форма отчёта, записи конверта, правила обмена `protocol`. Правила обмена пишет ядро по-английски | Решение «добавить во вход» в схеме не имеет формата |
| A3 | Текст для модели лежит в пакете: файл `.md` с тем же именем, что файл манифеста, рядом с ним. Задача хранит свою копию. Файл больше 64 КБ или не обычный файл: сценарий не подключается | В манифесте нет поля с инструкцией. Что делать модели, решает пакет |
| A4 | Результат сбора больше 2000 байт клиент получает как файл `{file, bytes}` рядом с задачей | Схема экземпляра: большой дифф не идёт во вход целиком |
| A6 | Команда `open` не открывает сценарий с проверкой вида «команда», «артефакт» или «внешнее состояние». Команда `report` для задачи в состоянии «проверка» запускает сверку снова | Ядро эти проверки ещё не запускает: задача осталась бы в проверке без выхода |
| A7 | Команда `finish` завершает публикацию. Команда `report` при ответе `PASS` с записями в конверте отвечает состоянием `publishing` и списком записей `writes` | Клиенту нужен явный конец публикации |
| A8 | Команда `stop` останавливает задачу в любом открытом состоянии от имени человека. Команда `tasks` даёт список открытых задач. Хук спрашивает человека перед командой `reins stop` | Прерванную задачу в исполнении и свободную задачу сессии нечем было закрыть. Команду может набрать агент, поэтому клиент спрашивает. Это совпадение текста команды: вызов через переменную или `eval` проходит |
| A5 | Конфигурация `~/.config/reins/config.json` называет каталоги пакетов и каталог состояния. Пакета проекта по каталогу репозитория ещё нет | Нужна одна точка, где клиент узнаёт пакеты |

Не покрыто: утверждение человеком через ядро вне хука (`confirm`, ответ на ожидание), связь задачи с сессией клиента, проверка клиента в живой сессии Claude Code с установленным плагином.

## Клиент: перед действием

Код: `src/client/before.ts` (`beforeAction`, `afterAction`), `src/client/config.ts`, `clients/claude-code/hooks` (хук и его регистрация), `clients/claude-code/tools.json` (инструменты самого клиента).

| № | Отличие от схем | Причина |
|---|---|---|
| B1 | Что делает инструмент, говорят два места. Адаптер клиента описывает свои инструменты: чтение, правка файла, команда оболочки. Пакет организации описывает инструменты коннекторов: раздел `tools` в `pack.json`. Инструмент без описания это запись (R1) | Схема коннектора задаёт действия, но не связь с именем инструмента клиента |
| B2 | Описание в пакете: имя инструмента (в конце допустима `*`, побеждает самое длинное имя), вид `read` или `write`. Запись называет действие из списка пакета, цель с полями входа `{поле}` и среду. Описывать инструменты может только организация | Нижний уровень иначе превратил бы запись в чтение |
| B12 | Значение в цели записи приводится к одному написанию: `a%2Fb` и `a/b` это одна цель. Так заполняются и конверт задачи, и вызов инструмента | Клиент может передать путь проекта с процентами |
| B3 | Цель записи, которую нельзя собрать из входа, делает действие неизвестным: ответ «спросить» | Иначе конверт покрыл бы запись в неизвестное место |
| B4 | Задачу для конверта ядро находит по записи конверта (действие, цель, среда) среди исполняемых задач, а не по сессии клиента. Подтверждённая запись конверта действует в любой сессии на этой машине, пока задача исполняется | Клиент не сообщает оболочке номер сессии. Запись конверта называет одну цель |
| B5 | Ответ человека на вопрос «одно утверждение на задачу» ядро узнаёт по событию «после действия»: инструмент выполнен, значит человек разрешил. Тогда запись конверта подтверждена и первое использование засчитано. Подтверждение принимается только в режимах клиента `default`, `acceptEdits`, `plan`: для остальных документация не обещает вопрос человеку | У клиента нет отдельного события «человек ответил» |
| B6 | Действие вне сценария принадлежит свободной задаче сессии клиента: одна на сессию. Два хука с устаревшим файлом сессии могут открыть две задачи: лишняя остаётся в журнале без действий | Журнал требует задачу у каждого решения политики. Событие «запрос человека» ещё не подключено |
| B7 | Защита самого харнеса: правка файла в каталоге состояния или файла конфигурации это отказ, правка пакета это вопрос человеку. Команда оболочки, в тексте которой есть путь каталога состояния, файла конфигурации или пакета (также в виде `~/` и `$HOME/`), это вопрос | Иначе агент подделает задачу, утверждение или список пакетов |
| B11 | Правка кода харнеса или адаптера клиента это вопрос человеку. Каталог называет адаптер | Таблица инструментов адаптера решает, что считать чтением |
| B8 | Адаптер Claude Code говорит «разрешить» вслух только когда действие покрыл конверт. Для остальных разрешённых действий он молчит: действуют собственные правила клиента | Явное «разрешить» от хука отменяет вопросы самого клиента |
| B9 | Решение «отложить» адаптер Claude Code переводит в отказ | Схема клиента: клиент без очереди считает такое действие отказом |
| B10 | Сбой адаптера: для чтения молчание, для остального вопрос человеку. Неизвестная форма входа хука: вопрос и строка `harness.client_shape_changed`. Сбой загрузки адаптера: вопрос. Сбой самого Node или срок клиента закрывает поле `onFailure: block` в регистрации хука: оно есть в документации Claude Code с версии 2.1.295, в живом клиенте не проверено. В более старом клиенте такой сбой пропускает действие | Схема клиента, страница 4 |

Не покрыто: разбор команды оболочки на запись в каталог состояния, конфигурацию и пакеты (сейчас совпадение текста: относительный путь после `cd` проходит), правила gate по уровням пакетов, очередь отложенных действий, события «начало сессии», «запрос человека», «отчёт», «конец сессии», определение уровня клиента, быстрый путь без запуска Node (сейчас около 220 мс на вызов), закрытие свободной задачи сессии.

## Части в рабочем минимуме

Эти части сделаны вширь: каждая работает на простом случае, детали отложены.

| Часть | Код | Что работает | Отложено |
|---|---|---|---|
| События клиента | `src/client/session.ts`, хуки Claude Code | Старт сессии даёт агенту сценарии, открытые задачи, записи памяти под вето, предложения крафта и заметки пакетов. Запрос человека открывает свободную задачу. Остановка агента закрывает её с меткой «не проверено». Конец сессии забывает сессию | Сжатие контекста, подчинённые исполнители, уровень клиента, привязка задачи сценария к сессии |
| Память | `src/memory/store.ts` | Запись ловушки, случая и состояния из задачи сценария по разрешению манифеста. Класс `veto`: запись ждёт семь дней. Решение пишет только человек. Вето, поиск по пути, команды `reins memory` | Срок вето из пакета, устаревание по якорю, перенос записей из `exocortex`, чтение памяти скриптом сбора, слияние дублей |
| Слои политики | `rules` в `pack.json`, `src/client/before.ts` | Правило любого уровня: «спросить», «отложить» или «отказать» по имени инструмента, действию, среде, тексту команды. Побеждает самое строгое. Вопрос правила снимает конверт задачи, как любой вопрос. Отказ не снимает ничто | Правила `gate` по уровням, разбор команды, очередь отложенных действий |
| Журнал | `src/journal/metrics.ts`, `reins status` | Счётчики задач, сценариев, проверок, решений, попыток записи в защищённое, сбоев и памяти за период | Восемь метрик спецификации по именам, ротация файла, поля данных для 37 видов событий |
| Проверка готовности | `scriptCheck` в `src/core/runtime.ts` | Виды «команда», «артефакт», «внешнее состояние»: решает скрипт пакета `check/<имя>`. Скрипт получает JSON на стандартный ввод (`task`, `inputs`, `report`, `collected`) и печатает `{"outputs":{"result":"PASS"},"flags":{}}` или `FAIL`. Нет скрипта, сбой или другой вывод: нет ответа. Скрипт идёт без блокировки задачи, ответ применяется под блокировкой и только к задаче, которая всё ещё ждёт проверку | Привязка ответа к состоянию работы, ограничение скрипта проверки, разные протоколы для трёх видов |
| Крафт | `src/craft/craft.ts`, `reins craft` | Два детектора: повтор вопроса по одному правилу и частый `FAIL` сценария. Предложение создаётся один раз, решает человек | Замер эффекта, остальные детекторы, текст предложения с готовой правкой |
| Срок задачи | `src/core/sweep.ts`, `reins sweep` | Свободная задача живёт 12 часов, задача сценария сутки, публикация час. Проверка идёт на старте сессии | Сроки из пакета, запуск по расписанию без сессии |
| Пакеты | `src/client/config.ts`, `pack.md` | Пакет проекта находится в `.reins` в корне репозитория, если конфигурация разрешает это ключом `repo_packs`. Каталог `.reins` любого репозитория защищён от агента всегда. Файл `pack.md` любого уровня попадает во вход каждой задачи и в старт сессии | Умолчания модели, сужение заметок нижним уровнем |
| Итог запроса по фактам | `src/core/work.ts`, `agentStopped` | Отпечаток рабочего дерева на запросе и на остановке. Если запрос изменил дерево, клиент показывает человеку метку «не проверено» | Возврат отчёта вне сценария, изменения вне репозитория |
| Передача состояния | `writeHandoff` в `src/client/session.ts` | Конец сессии оставляет счётчики и открытые задачи сценариев, следующая сессия начинает с них | Список задач сессии, несколько проектов |
| Пауза барьеров | `src/core/pause.ts`, `reins pause` | Вопрос проходит без вопроса на заданные минуты. Отказ и защита харнеса действуют | Пауза по одному правилу |
| Настройки клиента | `clientPaths` в адаптере | Правка файлов настроек клиента и каталога его плагинов это вопрос человеку | Разбор команды оболочки |

Сравнение с `agentic` по функциям и порядок перехода: `docs/port/agentic-replacement.md`.

Не начато: задача с договором, несколько исполнителей и поле «модель», триггеры по расписанию и по событию, запуск без окна, второй клиент, контракт коннектора для скрипта сбора.

## Чего в коде нет

- Сопоставление вызова инструмента с правилами. Для команды оболочки это делает `src/gate`.
- Очередь отложенных действий.
